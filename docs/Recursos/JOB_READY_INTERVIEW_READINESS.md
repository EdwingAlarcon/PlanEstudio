# Ruta Job-Ready Interview Readiness + Portafolio Laboral

Esta ruta convierte tus labs, capstones y recursos de PlanEstudio en materiales concretos para aplicar a vacantes: CV tecnico, LinkedIn, README de portafolio, demo de 10 minutos, respuestas de entrevista, ingles tecnico y comunicacion remota.

No garantiza empleo. Tampoco convierte automaticamente los labs en experiencia laboral formal. Su valor esta en ayudarte a presentar evidencia real de aprendizaje y practica sin exagerar el alcance.

## Vacantes objetivo

Esta ruta aplica a todos los perfiles del plan:

- Power Platform Maker.
- Functional Consultant.
- Power Platform Developer.
- Dynamics 365 CRM Functional Specialist.
- Dynamics 365 CRM Developer.
- Power Platform Admin / Governance Specialist.
- CRM Migration / Legacy Consultant.
- Solution Architect en formacion.

## Resultado esperado

Al completar esta ruta, deberias tener:

- Un CV tecnico orientado a Power Platform/Dynamics 365.
- Un headline y resumen LinkedIn coherentes con tu nivel real.
- Un README de proyecto para al menos un capstone.
- Un guion de demo de 10 minutos.
- Respuestas STAR para discovery, UAT, incidente, aprendizaje y trabajo remoto.
- Respuestas tecnicas en espanol e ingles para tu perfil objetivo.
- Una forma honesta de explicar labs, proyectos simulados y certificaciones.

## Principio central: evidencia sin exagerar

La regla principal es simple: **presenta lo que hiciste como proyecto, practica o capstone; no como empleo si no fue empleo**.

| Evita decir | Mejor di |
|---|---|
| "Trabaje como consultor Power Platform para una empresa ficticia" | "Desarrolle un capstone simulado de consultoria Power Platform basado en un caso empresarial" |
| "Administre un tenant corporativo real" | "Documente un governance assessment simulado con PPAC, DLP, ambientes y licenciamiento" |
| "Migre un CRM legacy de produccion" | "Diseñe una estrategia de migracion CRM legacy con mapping, staging, reconciliacion y cutover" |
| "Tengo experiencia laboral en Dynamics 365" | "Tengo experiencia practica academica/proyecto con Dynamics 365 y evidencia documentada" |

Un entrevistador serio no espera que inventes experiencia. Espera que puedas explicar decisiones, limites, trade-offs y evidencia.

## CV tecnico

### Estructura recomendada

1. **Titulo profesional objetivo**
   - Ejemplo: `Power Platform Developer Junior | Dataverse | Model-Driven Apps | Power Automate | ALM`
2. **Resumen de 3 lineas**
   - Que sabes construir.
   - Que evidencia tienes.
   - Que rol buscas.
3. **Skills tecnicos agrupados**
   - Power Platform: Power Apps, Power Automate, Dataverse, Power Pages.
   - Dynamics 365: Sales, Customer Service, Customer Engagement.
   - Desarrollo: JavaScript, C#, plugins, Web API, ALM, Git.
   - Gobierno: PPAC, DLP, ambientes, security roles.
4. **Proyectos / capstones**
   - 2 a 4 proyectos con problema, solucion y evidencia.
5. **Certificaciones / aprendizaje**
   - PL-900, PL-200/PL-400/PL-600 si aplica.
   - PlanEstudio como ruta de aprendizaje, no como certificacion oficial Microsoft.

### Formula para bullets

Usa esta formula:

`Construido / diseñado / documentado + tecnologia + problema resuelto + evidencia verificable`

Ejemplos:

- Diseñe una app model-driven para gestion de solicitudes con Dataverse, business process flow y security roles; documente modelo de datos, matriz de seguridad y pruebas UAT.
- Implemente un flujo Power Automate con aprobaciones, manejo de errores y trazabilidad; documente escenarios exitosos y fallidos.
- Desarrolle un plugin C# para Dataverse con validacion de negocio, tracing y registro de pruebas unitarias.
- Documente una estrategia de migracion CRM legacy con mapping origen-destino, reglas de limpieza, staging conceptual y runbook de cutover.

### Frases prohibidas

Evita:

- "Experto" si no has trabajado en produccion.
- "Arquitecto" si solo has hecho labs introductorios.
- "Experiencia laboral" para proyectos academicos.
- "Domino" si solo has visto awareness.

Prefiere:

- "Experiencia practica en proyectos simulados".
- "Capstone documentado".
- "Evidencia academica/proyecto".
- "Conocimiento aplicado de".
- "Awareness de".

## Demo de 10 minutos

La demo debe mostrar criterio, no solo pantallas.

| Minuto | Que mostrar | Frase guia |
|---|---|---|
| 0:00-1:00 | Problema y objetivo | "El problema era..." |
| 1:00-2:00 | Arquitectura / modelo | "Decidi modelarlo asi porque..." |
| 2:00-5:00 | Flujo principal | "Este es el proceso end-to-end..." |
| 5:00-7:00 | Seguridad / ALM / errores | "Esto evita..." |
| 7:00-8:30 | Evidencia y validacion | "Lo valide con..." |
| 8:30-10:00 | Lecciones y mejoras | "Si tuviera mas tiempo, mejoraria..." |

Prepara siempre:

- Entorno abierto antes de la llamada.
- Capturas fallback si falla internet.
- README abierto.
- Diagrama simple.
- Respuesta para "que parte fue mas dificil".

## Respuestas STAR

STAR significa Situacion, Tarea, Accion, Resultado.

### Ejemplo: problema tecnico dificil

**Pregunta:** Cuentame de un problema tecnico dificil que resolviste.

**Situacion:** En un capstone de Customer Service, el flujo de casos no reflejaba correctamente el estado del SLA.

**Tarea:** Necesitaba diagnosticar si el problema estaba en la configuracion del proceso, en los datos de prueba o en la interpretacion del criterio de validacion.

**Accion:** Revise el modelo de datos, cree casos de prueba, documente los estados esperados, compare resultados y ajuste la configuracion antes de repetir UAT.

**Resultado:** Logre un flujo reproducible, documente el defecto y deje una matriz de validacion que explica como probar el caso.

### Ejemplo: cambio de alcance

**Pregunta:** ¿Como manejas cambios de alcance durante un sprint?

**Respuesta:** Primero separo si el cambio corrige un requisito mal entendido o si agrega valor nuevo. Luego documento impacto en tiempo, riesgo y dependencias. Si el cambio es critico, propongo reemplazar otra tarea del sprint; si no, lo paso al backlog con criterio de aceptacion.

## Ingles tecnico

Prepara respuestas cortas. No busques sonar perfecto; busca ser claro.

### Pitch de 45 segundos

```text
I am building my professional profile around Microsoft Power Platform and Dynamics 365. My strongest areas are Dataverse, model-driven apps, Power Automate, and solution lifecycle basics. I have documented capstone projects with data models, security roles, process flows, validation criteria, and lessons learned. I am looking for a junior role where I can contribute to configuration, support, automation, and continuous improvement.
```

### Preguntas tecnicas en ingles

| Pregunta | Respuesta breve |
|---|---|
| Explain Dataverse security roles. | Security roles define what a user can do with records, based on privileges and access levels. They should follow least privilege. |
| What is ALM in Power Platform? | ALM is the process to manage solutions across dev, test and production using source control, solution packaging and controlled deployments. |
| How do you troubleshoot a failed flow? | I check run history, inputs and outputs, failed actions, retry policy, connection references and error handling. |
| What is a model-driven app? | It is an app generated from the Dataverse data model, forms, views, business rules and navigation. |
| How do you explain a plugin pipeline? | A plugin runs on Dataverse events such as create or update, in stages like pre-validation, pre-operation and post-operation. |

## Comunicacion remota

En roles remotos o con clientes, escribir bien es parte del trabajo.

### Update diario

```text
Ayer: configure la tabla Solicitud, vistas principales y roles de seguridad.
Hoy: validare el flujo de aprobacion y documentare casos UAT.
Bloqueo: necesito confirmar si Finanzas puede ver todas las solicitudes o solo las asignadas.
Riesgo: si no definimos ese rol hoy, la prueba UAT puede retrasarse.
```

### Reporte de incidente

```text
Impacto: los usuarios no pueden completar aprobaciones desde las 10:20.
Alcance: afecta el flujo Solicitud-Aprobacion en ambiente TEST.
Hallazgo inicial: la conexion de Outlook expiro.
Accion en curso: renovar conexion y repetir ejecucion fallida.
Proximo update: 11:30 con resultado y causa raiz.
```

### Maker / Functional

- ¿Como decides entre Canvas y Model-Driven?
- ¿Como levantas requerimientos ambiguos?
- ¿Como defines criterios de aceptacion?
- ¿Como pruebas una regla de negocio?
- ¿Como entrenas usuarios resistentes al cambio?

### CRM Functional

- ¿Como modelas un proceso de caso a resolucion?
- ¿Que diferencia hay entre cola, equipo y security role?
- ¿Como validas un SLA?
- ¿Como documentas UAT?
- ¿Como explicas Sales lead-to-cash?

### Developer

- ¿Cuando usas plugin en vez de Power Automate?
- ¿Como evitas recursion en plugins?
- ¿Como usas `formContext`?
- ¿Como consumes Dataverse Web API?
- ¿Como haces tracing y debugging?

### Admin / Governance

- ¿Que revisas primero en PPAC?
- ¿Como defines estrategia de ambientes?
- ¿Como explicas DLP a negocio?
- ¿Que revisas en capacidad/licenciamiento?
- ¿Como operarias un CoE moderno?

### Migration / Legacy

- ¿Como clasificas una migracion compleja?
- ¿Por que usar staging?
- ¿Como validas integridad post-carga?
- ¿Que revisas en CRM on-prem lento?
- ¿Que debe incluir un cutover runbook?

### Architect

- ¿Como traduces requerimientos en arquitectura?
- ¿Como decides entre configuracion y custom development?
- ¿Como manejas riesgos de integracion?
- ¿Como documentas una decision arquitectonica?
- ¿Como explicas trade-offs a negocio?
